How Stashling Stores Each Piece of a File Only Once

November 12, 2026 - by the Stashling maintainers - 6 min read

People often ask us how a year of daily backups of a 40 GB home folder can fit in less than 60 GB of storage. The short answer is deduplication: Stashling never stores the same piece of data twice. The longer answer is in this post, and it explains a change we made in version 2.4 that makes backups of large files much smaller.

Files are split into chunks

When Stashling reads a file, it does not save the file as one block. It cuts the file into chunks of about 1 MB and computes a hash of each chunk. The hash works like a fingerprint: two chunks with the same content always have the same hash. Before it uploads a chunk, Stashling checks its index. If the hash is already there, the chunk is already in your repository, and Stashling only writes a short note that says "this file uses that chunk".

This is why the second backup is so fast. Most of your files did not change since yesterday, so every one of their chunks is already stored. Stashling reads them, hashes them, finds them in the index and moves on. You can see the numbers for each run on the settings page, in the snapshot table.

Why fixed-size chunks were not enough

Until version 2.3, the chunks had a fixed size. The first chunk was bytes 0 to 1,048,575, the second chunk started right after it, and so on. That works well when a program changes a file in place. It works badly when a program inserts data near the start of a file.

Think of a large text file, a mailbox file or a virtual machine disk. If you add one line at the top, every byte after it moves down. Every fixed-size chunk now has different content, so every hash is new, and Stashling uploads the whole file again. One added line can cost you 4 GB of storage.

Chunks that follow the content

Version 2.4 uses content-defined chunking. Instead of cutting at fixed positions, Stashling slides a small window over the data and computes a rolling hash of the last 64 bytes. When the rolling hash matches a pattern, it cuts there. The pattern is chosen so that a cut happens about once every megabyte on average, with a minimum of 512 KB and a maximum of 8 MB.

Because the cut points depend on the content and not on the position, an insertion only changes the chunk where it happens. The bytes after it move, but the cut points move with them, and every following chunk keeps its hash. In our tests, adding one line to the top of a 4 GB mailbox file now uploads 1.3 MB instead of 4 GB.

$ stashling backup ~/Mail
scanning 1 file, 4.02 GB
new chunks:      2 (1.3 MB)
reused chunks: 4,117 (4.02 GB)
snapshot 9be04d7 saved in 41s

What you need to do

Nothing, for new repositories. For a repository made with an older version, the new chunker starts with the next backup. The first backup after the upgrade will be larger than usual, because the old chunks and the new chunks do not match. After that, your backups shrink again. Old snapshots stay readable, and you can restore any of them as before.

If you want to keep the old behavior, for example because your storage charges per upload, set chunker = "fixed" in your config file. The download page has the full upgrade notes.
